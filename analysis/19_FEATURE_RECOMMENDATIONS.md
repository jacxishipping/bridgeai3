# 19 — Feature Recommendations

> **Method.** Each opportunity from Part 12 of the brief is evaluated against the **real** architecture found by the audits (reports 01–16, DEPLOYMENT, DISTRIBUTED), not the docs. **Value** = user/business value if it works. **Effort** = S/M/L relative to this codebase. **Risk** = what breaks if done badly. **Verdict** is one of: **Build** (architecture supports it now), **Build after prerequisite** (named), **Defer** (real value but the foundation is not there), **Reject** (architecture cannot support it yet, or it conflicts with the product's security model). No feature is recommended that would widen the attack surface before the P0/P1 bypasses in report 17 are closed — that ordering is stated explicitly per item.
>
> **Standing constraint (all items).** The control plane is a 5,147-line monolith that is not multi-worker safe (DIST-01/03/04/07), the MCP layer has no audit trail (F-06-09), and approval can be bypassed via three alternate entry points (SEC-01/02/04). Any feature that adds a new entry point, a new background writer, or a new cross-worker interaction **inherits** those defects. Features marked "Build after prerequisite" name the prerequisite finding(s) from report 17.

## 4. Reject — architecture cannot support yet, or conflicts with the security model

| # | Idea (from Part 12) | Why rejected now | What would change the verdict |
|---|---|---|---|
| FR-R01 | **Multi-region / multi-plane federation** | No replication, no queue, no shared pub/sub, wall-clock ordering, tenant unenforced (report 14 §7: "do not attempt without a redesign"). Federation would multiply every DIST finding by the number of planes. | FR-19 delivered as an architecture programme first. |
| FR-R02 | **Public / multi-tenant SaaS offering** | Tenant is caller-supplied (SEC-03, P0); cross-tenant read by any viewer. A SaaS offering on this code would be a data-breach product. | SEC-03 fixed + tenant-scoped tests + independent audit. |
| FR-R03 | **Unattended Tier-4 by default for new fleets** (the current Linux default, as a product choice) | This is already the de-facto default (F07-02, P0) and is the single most dangerous product decision in the tree. Do not productise it; remove it. | Never — Tier 4 unattended must remain opt-in, approved, and audited. |
| FR-R04 | **AI-driven auto-approval** (model decides whether an action needs approval) | Approval is the last control that (mostly) works on `/api/tasks`; the bypasses are in the entry points, not in the approval logic. Letting a model waive approval removes the control before the bypasses are closed. | All SEC-01/02/04 bypasses closed + approval audit complete (F-06-09). |
| FR-R05 | **More MCP tools before consolidation** (growing 109 → more) | 40 tiered tools already have no MCP exposure and 5 exposed tools are untiered (F-06-04); ~40 wrappers have no policy call (F-06-05). Adding tools to this surface adds unaudited, ungated surface. | TD-D01 + TD-P01: one registry, one gate, then grow. |
| FR-R06 | **Native (C++) WebRTC as the default streaming path** | C++ path is opt-in, default OFF, drops viewer ICE candidates, has no TURN, and its encoder fabricates success (F08-01, F13-05, F08-19 stub backend). Making it default would regress the working Python path. | F08-01/02/03/05 fixed + C++ path wired to the dashboard + E2E test with a real browser peer. |

## 5. Sequencing (this synthesis)

1. **Now:** FR-01, FR-03, FR-05, FR-06, FR-07, FR-08 — all small, all reduce risk or false confidence, none needs a prerequisite.
2. **Next (after the P0/P1 fixes in report 20):** FR-02, FR-04, FR-20, FR-10, FR-13.
3. **Later (architecture programme):** FR-09, FR-12, FR-15, FR-16, FR-18, FR-19.
4. **Do not start:** FR-R01–R06 until their stated conditions are met.
